# Incident Witness Protocol v1 — Design Reference

**Status:** Protocol v1 is implemented in `packages/protocol`; API-side event ingestion, deterministic correlation (`@incident-witness/correlator`) and bundle sealing/download are implemented in Phase 3C. Host agent, renter SDK and probe worker are implemented in Phases 3D–3E. The Phase 3F offline CLI verifier and synthetic demo harness are accepted. Phase 4 connects the provider workspace and a local browser verifier to the staging API; bundle verification still runs entirely locally. This document must remain consistent with `ARCHITECTURE.md` and the protocol/correlator tests.

## Purpose

Define an interoperable, signed event and bundle format for recording limited observations from provider, renter and platform-operated probe sources. It is not a claim that these sources are truthful or independent of their operators.

## Source types

- `host_agent`: key generated by a provider's Linux host agent and registered to one host.
- `renter_client`: key generated by a renter SDK and scoped to one evidence session.
- `platform_probe`: key controlled by the Incident Witness service and used by the external probe worker.

Do not name `platform_probe` `independent_witness`. It is operated by the platform.

## Required event fields

```json
{
  "protocol_version": "1.0",
  "event_id": "uuid",
  "incident_id": "uuid",
  "source_key_id": "uuid",
  "source_type": "host_agent",
  "event_type": "host_heartbeat",
  "sequence": 42,
  "observed_at": "2026-10-30T12:00:00.000Z",
  "payload": {},
  "simulation_mode": false,
  "canonicalization": "RFC8785-JCS",
  "signature_algorithm": "Ed25519",
  "signature": "base64url-without-padding"
}
```

The example is structural only; an actual event must satisfy its typed payload schema. Do not add arbitrary properties. `signature` is computed over the canonical event body with the signature field omitted. The complete request envelope, including its signature, is sent in canonical form. Operational-presence heartbeats are separately domain-separated and also require a canonical full request envelope. `received_at` is added by the server after signature verification and is never included in the source signature.

## Cryptographic rules

1. Validate strict protocol schemas and I-JSON compatibility: reject unknown fields, undefined/non-JSON values, non-finite or unsafe integers and unsupported object types. `sequence` is a positive safe integer no greater than `Number.MAX_SAFE_INTEGER`; database storage may be `bigint` but the wire format may not exceed the safe integer range.
2. Canonicalize using RFC 8785 JCS with the exact pinned `canonicalize@5.1.0` implementation. Do not write a custom canonicalizer or use informal JSON stringification.
3. Hash canonical bytes using SHA-256.
4. Sign canonical bytes using Ed25519.
5. For event ingestion, send the complete envelope as exact canonical UTF-8 bytes using `Content-Type: application/vnd.incident-witness.event+json`. The API must preserve raw bytes and reject any body that does not exactly equal JCS serialization of the parsed object; this rejects duplicate property names and noncanonical wire representations before signature verification.
6. Encode key/signature bytes base64url without padding.
7. Server verifies using the registered source public key and checks the key's source scope/status.
8. The bundle platform signature covers the canonical manifest; its digest is included for convenience and tamper reporting.
9. Offline verification trusts only a platform public key whose fingerprint is pinned by the verifier release. A public key included inside a file is not trusted merely because the file includes it.

## Source key certificate

A platform-signed registration certificate includes certificate version, source key ID/type, source public key, fingerprint, host or incident scope, issued time and protocol version. The certificate confirms registration by the service under a defined workflow. It does not confirm a hardware identity, legal identity or uncompromised host.

## Event types and payload boundaries

| Event | Fields permitted |
|---|---|
| `host_heartbeat` | agent version, OS family/version, uptime and agent health (sequence is the outer envelope field) |
| `host_power_state` | configured UPS alias, allowed state enum, battery charge %, runtime seconds |
| `gpu_telemetry` | device index, vendor/model, temperature C, utilization %, memory used/total MiB, power draw W, driver version if safely available, collection status |
| `host_agent_status` | start/stop/recovery signal, agent version, status enum |
| `renter_heartbeat` | SDK version, workload reference ID, client state |
| `renter_endpoint_result` | result enum, latency ms, bounded failure category |
| `platform_probe_result` | probe status, DNS/TLS/HTTP result categories, latency, bounded response classification |
| `source_gap` | source key/type, expected interval, missing interval and reason code; platform-signed when generated by service |

No arbitrary logs, shell output, process lists, host environment variables, customer prompts, model inputs/outputs, datasets, credentials or unrestricted network addresses are permitted. A source event payload is capped at 2 KiB, the full event-ingestion request at 8 KiB, each incident at 4,000 accepted events and 7 MiB aggregate serialized bundle event-entry bytes, and the complete bundle at 10 MiB. `INCIDENT_EVIDENCE_LIMIT` rejects any event that would breach count or aggregate byte limits. The aggregate byte counter is incremented atomically with the event insert. Bundle sealing rechecks the exact final canonical bundle size and fails atomically rather than truncating evidence.

## Sequence and time semantics

- Sequence is a positive safe integer, monotonically increasing per source key across all event types, and persists through restart. The API/database may store it as `bigint` but must reject values above `Number.MAX_SAFE_INTEGER` at the JSON protocol boundary.
- Unique `(source_key_id, sequence)` and event UUID prevent replay/duplicates.
- Exact duplicate event request is idempotent; same ID with different body is a conflict.
- Out-of-order observations may be accepted within the incident/grace window; timeline order is deterministic: observed time, source type, key ID, sequence, event ID.
- Source time and server receive time are separate. Future timestamps beyond five minutes are rejected. Clock skew creates a quality warning; source time is not silently rewritten.
- `observed_at` must fall inside `[capture_started_at, capture_ends_at]`; observations outside the capture window are rejected even if they arrive during grace.
- Server-generated `received_at` may be recorded only up to the incident ingestion deadline (capture end + 24 hours). Grace permits delayed transmission of an in-window observation, not post-capture observation.
- Session capture window is bounded; 24-hour grace allows local spool sync after capture ends.

## Bundle format

Version `1.0` contains:

- `bundle_version` and `manifest`.
- Incident ID, host pseudonymous reference/alias, verified hostname, capture and seal times.
- Protocol and rule versions.
- Ordered source events and server receipt times.
- Source public keys and signed registration certificates.
- Event digests, sequence/gap warnings and simulation markers.
- Assessment code, deterministic explanation and evidence grade.
- Explicit limitations notice.
- Platform key ID, manifest SHA-256 and Ed25519 signature.

The bundle is private to provider account until the provider intentionally downloads it. It may reveal host alias, hostname, operational telemetry and timeline. Inspect before sharing.

## Verification semantics

Verification checks schema, canonical digest, trusted platform key, platform signature, source certificates, source event signatures, event ordering/sequence consistency and bundle consistency. A success says the bundle and signatures verify relative to the trusted key set. It does not prove reading truth, physical cause, source independence, key security or marketplace acceptance.

## Deterministic assessments

Supported v1 outputs: `POWER_RELATED`, `EXTERNAL_REACHABILITY_LOSS`, `HOST_OR_WORKLOAD_EXIT`, `UNKNOWN`. GPU/driver anomaly is not classified in v1 because the baseline collector does not provide a sufficiently validated fault signal; such cases remain UNKNOWN. Output wording must say “consistent with” or “observed”; no absolute causal conclusion. Evidence grades HIGH/MEDIUM/LOW/INSUFFICIENT describe evidence completeness under a named rule version—not probability. Simulated decisive signals cap grade at LOW. Demo sessions carry a top-level demo marker in the manifest.

### Rule version `iw-rules-v1`

- Correlation window: 120 seconds around the first relevant transition.
- Power chain window: 180 seconds from the UPS transition.
- Probe/host adjacency: 30 seconds between a platform-probe failure and a signed host heartbeat/agent-health observation.
- `POWER_RELATED` requires a host UPS `on_battery`/`low_battery` transition, a prior host heartbeat, no host heartbeat in the following power window, and a renter or probe reachability failure near the transition.
- `EXTERNAL_REACHABILITY_LOSS` requires a platform-probe failure and a host heartbeat/agent-health observation within 30 seconds; renter endpoint failures may corroborate. UPS online alone is not sufficient.
- A `platform_probe_result` with `probe_status: error` represents a probe infrastructure/policy failure (for example an unsafe DNS answer) and is excluded from causal rules; it is not evidence that the provider host is down.
- `HOST_OR_WORKLOAD_EXIT` requires an explicit host-agent `stopped` or renter-client `stopped` signal plus a supporting probe/client observation in the correlation window.
- `HIGH` requires three decisive source categories, `MEDIUM` two with at least one external to the host, `LOW` one or a simulated decisive signal, and `INSUFFICIENT` zero usable observations. The correlator is pure and input-order independent.
- `event_sha256` is SHA-256 over the canonical event body without `signature`; `manifest_sha256` is SHA-256 over the canonical manifest. The platform signature covers the canonical manifest.

## Compatibility

- Unknown protocol major version: reject as unsupported; never guess.
- Unknown required field/event type: reject.
- New optional fields require protocol change/versioning and fixtures.
- Old bundles remain verifiable as long as their signing key remains trusted and verifier retains schema support.
- Publish golden canonical byte/signature fixtures in `tests/fixtures` and run in API, web and CLI.
